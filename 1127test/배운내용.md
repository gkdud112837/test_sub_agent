## 1. 데이터 모델링

- 순서: 서비스 문장의 명사 → 테이블 → 열과 형식 → "하나에 여러 개" 관계 → 외래키 → **예시 행 3개로 검증**
- 예시 행을 직접 채워 보니 빠진 열이 두 개 나왔다.
  - `orders.survey_id`: 어느 추천에서 나온 주문인지
  - `ordered_at`과 `created_at`의 구분: CSV로 넣은 과거 주문은 "주문한 시각"과 "DB에 들어간 시각"이 다르다
- 추천 결과는 저장하지 않았다. 설문 + 상품으로 다시 계산할 수 있으니 중복이다.

## 2. 키 · 환경변수 · 놓이는 자리

```text
코드 → GitHub · 실행 → Vercel(app/api 서버 함수) · 데이터 → Supabase · 비밀값 → 환경변수
```

| 키 | 위치 | 노출되면 |
|---|---|---|
| publishable (`NEXT_PUBLIC_`) | 브라우저 가능 | RLS가 허락한 행만 → RLS가 꺼져 있으면 테이블 전체 노출 |
| secret | 서버 전용 | RLS를 건너뜀 → 모든 데이터 수정·삭제 |
| Gemini | 서버 전용 | 남이 내 한도를 씀 |

- `import "server-only"`를 secret 클라이언트와 Gemini 모듈 맨 위에 두면, 클라이언트 컴포넌트가 실수로 import할 때 **빌드가 실패한다**. 사람의 주의 대신 도구로 막는 방법이다.
- 빌드 뒤 `.next/static`을 grep하면 키 노출을 직접 확인할 수 있다. `sb_secret_`가 한 곳 걸렸는데, supabase-js가 키 접두사를 판별하는 코드였다. **검색에 걸렸다고 바로 노출은 아니다. 문맥을 열어 봐야 한다.**

## 3. GRANT와 RLS — 문과 자물쇠

- GRANT = 테이블에 들어오는 문(역할 단위), RLS = 행마다 거는 자물쇠.
- anon에게 orders GRANT가 없으면 RLS까지 가기 전에 `42501`이 난다. 교안의 "빈 결과"와는 다르지만 둘 다 행은 0개다. spec에 이 차이를 적어 두었다.
- **GRANT만 추가하고 revoke를 하지 않으면** 프로젝트 기본 권한(anon에게 ALL)이 남을 수 있다. 리뷰 서브에이전트가 찾은 문제다. 그래서 `revoke all` → 필요한 것만 `grant` 순서로 바꿨다.
- 쓰기 정책은 하나도 만들지 않았다. 쓰기는 모두 서버(secret 키) 경유다.
- 재고 차감 + 주문 기록은 `place_order` 함수의 조건부 update 한 문장으로 처리했다. 동시에 주문해도 재고가 음수가 되지 않는다. 함수 EXECUTE 권한은 service_role에만 있다.

## 4. Supabase 없이 SQL 검증하기 — PGlite

- `@electric-sql/pglite` = WASM으로 돌아가는 진짜 Postgres다. 설치만 하면 된다.
- Supabase가 주는 것을 흉내 냈다: `anon`·`authenticated`·`service_role` 역할, `auth.users`, `auth.uid()`(= `current_setting('request.jwt.claim.sub')`).
- `SET ROLE anon`으로 publishable 키 상황을 재현하고, `set_config('request.jwt.claim.sub', A)` + `SET ROLE authenticated`로 로그인 사용자 A를 재현했다.
- 한계: 실제 프로젝트의 기본 권한·Auth 설정은 재현하지 못한다. 그래서 "가장 열린 기본 권한"을 일부러 걸어 놓고 검증했다.

## 5. 앱 안 AI 기능의 네 가지 규칙

1. 키는 서버에서만, URL이 아니라 `x-goog-api-key` 헤더로 보낸다.
2. 출력 형식 고정: `responseMimeType: application/json` + `responseSchema`. **서버에서 다시 검사**한다(배열 · 후보 id · 길이 · 숫자 없음).
3. 근거 제한: DB 값과 설문 선택지만 넣는다. 자유 입력(메모)은 프롬프트에 넣지 않는다(프롬프트 주입 차단).
4. 실패 대비: 키 없음 · 429 · 8초 초과 · 형식 오류가 나면 DB 값으로 만든 기본 문구를 쓰고 화면에 "기본 문구" 꼬리표를 단다.

## 6. 리뷰 서브에이전트가 찾은 의외의 문제

- **오픈 리다이렉트**: `next.startsWith("/") && !startsWith("//")` 검사는 `/%09/evil.example`(탭)로 뚫린다. `new URL()`이 탭을 지워 `//evil.example`이 되기 때문이다. → 문자열 검사 대신 **URL을 해석해 origin을 비교**하는 방식으로 고쳤다.
- 레이트 리밋이 없으면 비로그인 사용자가 재고를 0으로 만들고 수요예측 데이터를 오염시킬 수 있다. → 메모리 제한을 넣었다(인스턴스마다 따로 세는 한계가 있어 운영 전에 공유 저장소로 바꿔야 함).
- 글자 수로 잰 4KB 제한은 한글이면 바이트로 3배까지 통과한다.
- 교훈: "문제 없음"이라고 한 범위 밖은 모른다. 수용 기준은 사람이 배포 URL에서 직접 테스트한다.

## 7. SQL 기초 · 시간대

- 읽는 순서: FROM·JOIN → WHERE → GROUP BY → SELECT → ORDER BY·LIMIT
- `AT TIME ZONE 'Asia/Seoul'`을 빼면 가상 주문 304건 중 20건(한국 시간 0~9시)이 전날 요일로 넘어가 요일별 합계가 바뀐다(금 65 → 67 등).
- 검산은 SQL 밖에서 따로 센다: CSV에서 상품 2의 수량 합 55 + 테스트 주문 3 = 58 = SQL 결과.

## 8. 보충: 통계 분석 다섯 실습 (모두 재현, 교재 수치와 일치)

- 한 행 = 운송 구간이다. 주문 매출을 행 그대로 더하면 147.4억으로 3.1배 부풀고, 주문별로 한 번만 더해야 47.2억이다.
- p값(우연인가)과 크기(%p, 크라메르 V 0.25)는 따로 적는다.
- 층화하면 기상 효과는 **선사 구간에만** 있다(34.1% → 92.6%). 실습 1의 73.3%는 섞인 평균이다.
- 선사 5곳 신뢰구간이 모두 겹친다(p = 0.63). 순위를 매기기 전에 오차부터 본다.
- 모델 69.0% ≈ 규칙 하나 69.1%로, 신호가 없으면 모델도 못 맞힌다. 누설 열을 넣으면 98~100%가 된다.
- 납기는 분위수로 약속한다. 독일·브라질은 최단 소요일 39·43일이라 D+30은 처음부터 지킬 수 없다.
- 교재는 "2024년 주문"이라고 했지만 실제로는 2023~2025년이 섞여 있다.
