## 2. 중요하다고 생각하는 내용

### ① 비밀 키는 "주의"가 아니라 "구조"로 막는다
- secret 클라이언트와 Gemini 모듈 맨 위에 `import "server-only"`를 둔다. 클라이언트 컴포넌트가 실수로 import하면 **빌드가 실패한다**.
- 서버에도 클라이언트가 두 종류다. **publishable 키 + 로그인 쿠키**(RLS 적용)는 읽기와 본인 조회에, **secret 키**(RLS 우회)는 쓰기(설문 저장 · 주문)에만 쓴다. 최소 권한을 코드 구조로 표현했다.
- 빌드 뒤 `.next/static`을 grep해서 직접 확인한다. 검색에 걸려도 바로 노출은 아니다. 이번에 걸린 `sb_secret_`는 supabase-js의 접두사 판별 코드였다.

### ② GRANT는 문, RLS는 자물쇠 — 둘 다, 그리고 "회수"까지
- GRANT를 추가만 하면 프로젝트 기본 권한(anon에게 ALL)이 남을 수 있다 → `revoke all` → 필요한 것만 `grant`.
- 쓰기 정책은 0개로 두고, 쓰기는 서버 함수로만 한다. 재고 차감은 조건부 update 한 문장이라 동시 주문에도 음수가 되지 않는다.
- 교안의 "publishable 키로 orders 조회 시 빈 결과"는 우리 구조에서 `42501`로 나온다. GRANT에서 먼저 막히기 때문이다. 둘 다 행 0개다. 이 차이를 spec에 적어 두었다.

### ③ 계정이 없어도 SQL은 검증할 수 있다 — PGlite
- WASM Postgres에 Supabase 역할(anon · authenticated · service_role)과 `auth.uid()`를 흉내 내면, `SET ROLE`로 publishable 키 상황과 로그인 사용자 A/B를 재현할 수 있다.
- 가장 열린 기본 권한을 일부러 걸어 놓고 테스트해야 #2 같은 문제를 잡을 수 있다.

### ④ 앱 안 AI는 "믿지 않는다"
- 출력 형식 고정(JSON 스키마) + **서버 재검사**(후보 id · 길이 · 숫자 금지) + 실패 시 DB 값으로 만든 기본 문구.
- 사용자 자유 입력은 프롬프트에 넣지 않는다(프롬프트 주입 차단). 추천 3개의 사유는 호출 한 번으로 받는다(한도 절약).

### ⑤ 리뷰 서브에이전트는 "고친 코드도 다시"
- 1차에서 직접 쓴 `startsWith` 검사가 탭 문자 하나로 뚫리는 **오픈 리다이렉트**가 나왔다. 문자열 검사 대신 URL을 해석해 origin을 비교하도록 바꿨다.
- 2차에서는 **고친 코드**(레이트 리밋)에서 새 문제가 나왔다. 위조 가능한 IP 헤더를 키로 쓰고 있었다.
- 리뷰 프롬프트에 "근거 줄을 열어 확인한 것만" · "문제 없음으로 확인한 것" · "보지 못한 범위"를 넣으면 보고서의 신뢰도가 달라진다.

### ⑥ 데이터는 "한 행이 무엇인가"부터
- 물류 엑셀은 한 행 = 운송 구간이다. 주문 단위 열 18개가 구간마다 반복돼, 행 그대로 합하면 매출이 3.1배(147.4억 vs 47.2억) 부푼다.
- 시간은 UTC로 저장하고 `AT TIME ZONE 'Asia/Seoul'`로 집계한다. 빼면 304건 중 20건이 전날 요일로 넘어간다.
- 검산은 SQL 밖에서 따로 센다(CSV 합 55 + 테스트 3 = 58).

### ⑦ 엑셀을 "그냥 보기만 해도" 보이는 것
- 같은 값 열 3쌍, 배송상태가 소요일로 100% 결정됨(= 결과값, 예측 입력 금지), 지연 사유가 기상 열과 규칙으로 맞물림, 운임 규칙(국내 = 해외, 선사 = 국내 × 2), 교재와 다른 기간(2023~2025).
- 통계를 돌리기 전에 이걸 먼저 봤다면 실습 4의 "정답 누설"과 실습 2의 "사유 코드는 검증된 원인이 아니다"를 미리 알 수 있었다.
